## 서버 과정 — 연동 환경이 있을 때 완료

- [ ] 조회한 사원 한 명의 이름을 변경하고 저장·재조회해 유지되는지 확인한다.
- [ ] 새 사원을 추가하고 저장·재조회해 다시 나오는지 확인한다.
- [ ] 직접 추가한 테스트 사원을 삭제하고 저장·재조회해 사라졌는지 확인한다.
- [ ] 실패 응답이 왔을 때 성공 메시지가 나오지 않는지 확인한다.

이름 수정은 화면 반영과 서버 반영을 구분해서 확인하세요. 서버가 준비되지 않았다면 학습 기록에 **‘로컬 완료 / 서버 실습 대기’**로 남기면 됩니다.

## 막혔을 때 찾는 표

| 증상 | 가장 먼저 볼 곳 |
| --- | --- |
| 버튼을 눌러도 반응이 없다 | onclick 속성과 함수 연결 |
| ID를 바꾸니 오류가 난다 | Script의 예전 ID, Div 내부 접근 경로 |
| Grid가 비어 있다 | Dataset Rows → binddataset → 컬럼 바인딩 |
| 목록은 나오는데 상세가 비어 있다 | 현재 행 → 상세의 value 바인딩 |
| Combo 목록만 보이고 선택값이 안 맞는다 | value 바인딩, 코드 값 일치 여부 |
| Grid에 부서 코드가 그대로 보인다 | body 셀의 Combo 표시 설정 |
| 수정한 화면이 실행에 반영되지 않는다 | 저장·Generate 결과, 실행 경로·Reload |
| 조회 후 바로 읽으면 이전 데이터다 | 결과 처리를 callback에서 하는지 |
| 저장 성공인데 재조회 결과가 다르다 | input 매핑·행 상태·서버 처리 결과 |

## 스스로 설명해 보기

1. Grid와 상세 화면이 같이 바뀌는 이유는?
2. Combo에 Dataset을 두 종류 연결하는 이유는?
3. 행을 추가한 것과 DB에 저장한 것은 어떻게 다른가?
4. `ds_emp=out_emp`와 `in_emp=ds_emp:U`의 데이터 이동 방향은?

<details>
<summary>답 확인하기</summary>

1. 같은 Dataset에 바인딩되어 있고 상세는 현재 행을 보여주기 때문입니다.
2. 하나는 선택 가능한 목록, 다른 하나는 현재 사원의 선택값을 제공하기 때문입니다.
3. 추가는 화면 Dataset 변경이고 DB 저장은 서버 요청과 처리가 필요합니다.
4. 조회는 서버 → 화면, 저장은 화면의 변경 데이터 → 서버입니다.

</details>
