# Dataset 컬럼은 어떤 기준으로 설계하나요?

[매뉴얼 목차](../../README.md)

**화면과 API가 필요한 데이터를 기준으로 설계하고 서버와 형식을 맞춥니다.** DB 테이블의 모든 컬럼을 그대로 복사할 필요는 없습니다.

## 역할부터 나누기

| 예시 | 역할 | 담을 값 |
| --- | --- | --- |
| ds_search | 조회 조건 | 부서 코드·검색어 |
| ds_emp | 사원 목록과 수정값 | 사번·이름·부서·급여 |
| ds_dept | 부서 선택지 | 코드와 표시명 |

여러 DB 테이블을 조인한 결과를 하나의 Dataset으로 받을 수도 있습니다. 화면에서 체크했는지 표시하는 값처럼 DB에 저장하지 않을 컬럼도 구분합니다.

## 컬럼을 정할 때 확인할 것

| 결정할 내용 | 예시 |
| --- | --- |
| 식별자 | 수정·삭제할 사원을 찾는 EMPL_ID |
| 이름·자료형·크기 | 서버 컬럼명, 문자열 길이, 숫자 정밀도 |
| 값의 표현 | null과 빈 문자열, 날짜 형식, 부서 코드 |
| 저장 대상 | 화면 선택용 값인지 DB 반영 값인지 |

사번은 숫자처럼 보여도 앞자리 0을 보존하려면 문자열이 필요할 수 있습니다. 날짜는 DATE인지 `yyyyMMdd` 문자열인지, 급여는 소수점과 범위를 어떻게 처리할지 합의합니다.

## 정의와 검증은 다릅니다

컬럼을 만들었다고 필수값·유일성·외래키가 DB처럼 보장되지는 않습니다. 화면과 서버에서 업무 검증을 구현합니다. 서버 연동 후에는 테스트 Rows가 실제 결과와 섞이지 않게 관리하세요.

조회 후 구조가 바뀐다면 서버 응답 컬럼과 `useclientlayout` 같은 설정을 확인합니다. 컬럼명만 같다고 자료형까지 같다고 가정하지 않습니다.
